1. OVERVIEW
==============================================================================
NHTS (No Headache Trading Strategy) is a NinjaTrader 8 strategy distribution
that automates multi-indicator confluence tracking for NQ, CL, and GC futures
trading. NHTS reduces the emotional and cognitive load associated with choppy
markets, noise, and false signals by monitoring multiple indicator conditions
simultaneously and alerting the trader — or automatically executing — when a
qualifying setup occurs.

NHTS is an independently developed strategy. It originated from the
ActiveNikiTrader codebase (which used third-party ninZa.co indicators), but its
indicator logic is now implemented in original, self-contained calculator
classes owned by Alex. NHTS does NOT aim to reproduce ninZa.co signals; its
objective is to OUTPERFORM the ninZa-based predecessor (see Section 3).


==============================================================================
2. PURPOSE AND SCOPE
==============================================================================
Primary objective:
* Deliver a strategy that outperforms the ninZa-based ActiveNikiTrader baseline
  on net realized PnL over a defined benchmark window, on identical market data
  (see Section 3). This is the defining success criterion for NHTS and takes
  precedence over signal fidelity to any predecessor indicator.

Supporting objectives:
* Provide audio and visual signals to NinjaTrader 8 traders when confluence and
  other conditions are met.
* Reduce emotional stress associated with choppy markets, market noise, and
  false signals by automating the task of tracking multiple conditions
  simultaneously.
* Provide an integrated analysis engine that processes trade session logs and
  surfaces optimization suggestions for trading hours, confluence thresholds,
  indicator selection, and exit parameters.
* Be distributable to non-technical traders with minimal setup friction.

3. PERFORMANCE VALIDATION & BENCHMARK   [NEW in v0.3]
==============================================================================
NHTS success is measured by performance, not by fidelity to ninZa.co indicators.
This section defines how "better" is measured so that every indicator, parameter,
or logic change can be judged objectively.

3.1 Primary Metric
* Net realized PnL over the benchmark window (Market Replay, deterministic).

3.2 Baseline
* Primary baseline: ActiveNikiTrader (ninZa-based predecessor) run on the
  IDENTICAL .nrd replay data and the same chart/strategy templates.
  NHTS must exceed ActiveNikiTrader net PnL over the window.
* Secondary floor [ASSUMPTION — confirm]: NHTS must also be net-positive
  (> $0) over the window, so "beats baseline" cannot be satisfied merely by
  losing less on a losing period. Adjust or remove if not desired.

3.3 Benchmark Window — NQ front-month, latest two roll cycles
  Roll convention used: "8-day rule" = second Thursday prior to the third
  Friday of the contract month (matches common trader practice).
    - MAR26 front-month window: Dec 11, 2025  ->  Mar 12, 2026
    - JUN26 front-month window: Mar 12, 2026  ->  Jun 11, 2026
  Alternative (CME-official) convention is the Monday prior to the third Friday
  (Dec 15 2025 / Mar 16 2026 / Jun 15 2026); switch here if preferred.
  Each window uses the contract that was the liquid front month during it.

3.4 Overfitting Guard & Robustness Protocol (mandatory)
The objective of this protocol is to BREAK a candidate configuration, not to
confirm it. A result that survives all tests below is treated as the real edge;
an impressive number that has not yet been attacked is treated as unproven.

  (a) Out-of-sample (train/test): the two windows (3.3) form a train/test split.
      A config tuned on one window MUST be re-run, parameters LOCKED (single
      Backtest run, not Optimization), on the other held-out window. A config
      that wins in-sample but not out-of-sample is rejected as curve-fitting.
  (b) Parameter plateau: a genuine edge sits on a plateau, not a lonely spike.
      Re-run the winning config with each key parameter nudged slightly
      (e.g. SL +/- one step, TP +/- one step, confluence threshold +/- 1).
      Profit must degrade gracefully, not collapse. A cliff = overfit.
  (c) Slippage stress: re-run at increasing slippage (e.g. 5, 8, 10 ticks).
      A config profitable only at low slippage is fragile.
  (d) Fill-resolution stress: re-run with Order Fill Resolution = High (stricter
      intrabar fills) instead of Standard (Fastest). Material profit loss means
      part of the result was optimistic fill assumptions, not edge.
  (e) Bar-construction sensitivity (UniRenko): because optimizing the bar
      parameters (Open Offset / Tick Reversal) fits the bars themselves to the
      data, re-run the winning strategy params on standard / un-optimized
      UniRenko settings. Heavy dependence on the exact bar parameters is the
      most fragile failure mode and is flagged accordingly.
  (f) Regime test (lower priority): once (a)-(e) pass, validate on a different
      instrument or an earlier date range. Surviving a regime change is the
      strongest robustness evidence.

  Backtest realism (apply to ALL robustness runs so numbers are trustworthy):
  * Commission: use a realistic per-contract round-turn (e.g. ~$4-5 for
    Apex/Rithmic). A $0 or "free" template understates costs; at high trade
    counts this is material. Verify the selected commission template's actual
    per-contract charge.
  * Slippage: minimum 1 tick (NQ) for the baseline run; stress higher per (c).

3.5 Secondary / Guardrail Metrics (reported alongside PnL; prevent fragile
    "wins")
* Maximum drawdown
* Win rate
* Profit factor
* Trade count (a "win" achieved on too few trades is not accepted)

3.6 Data Prerequisite
* .nrd Market Replay files for every session in the chosen window must be
  present on the test machine(s). (Alex maintains/copies these as needed.)
* The same .nrd files must be used for both NHTS and the ActiveNikiTrader
  baseline so the comparison is on identical bars.

3.7 Account-Size Modeling (deferred decision)
* NT8's Strategy Analyzer has NO account-size setting; it simulates an
  effectively unlimited account and reports raw cumulative PnL. Net-profit and
  drawdown figures are therefore capital-independent (valid for ranking configs)
  but do NOT model margin rejection or equity-based position sizing.
* DEFERRED DECISION: whether to model a $5,000 account with a daily margin
  limitation requirement (capital-constrained sizing / trade rejection when
  margin is insufficient). If adopted, this must be coded INTO the strategy
  (track an account-value variable, size/gate entries off it) since NT8 offers
  no built-in setting. Tracked as a milestone step under M_perf and an Open Item.

6. USE CASES
==============================================================================
6.1 Signal Monitoring
NHTS is attached to an NQ, CL, or GC chart in NinjaTrader 8. It continuously
evaluates the selected indicator set and displays real-time state in an on-chart
panel. When the configured confluence threshold is met, NHTS:
* Displays a directional signal (LONG / SHORT) in the panel.
* Plays an audio alert.
* Optionally sends an entry order to the broker automatically.

6.2 Confluence Configuration
The trader adjusts which indicators participate in the confluence vote directly
from the panel using checkboxes, without reloading the strategy.

6.3 Session Analysis
After a trading session the trader clicks Run Analysis in the NHTS panel (or
relies on a scheduled end-of-session task). NHTS generates an HTML report opened
automatically in the default browser, covering trade performance, time slot
analysis, and parameter optimization suggestions.

6.4 Scheduled Reporting
NHTS supports a configurable scheduled analysis task (e.g. end-of-session, daily)
that runs the analysis pipeline and optionally delivers the report by email.

8. INDICATOR SET
==============================================================================
8.1 Open, Performance-Driven Roster
The NHTS indicator roster is NOT fixed and is NOT tied to the ninZa.co set.
Indicators are included, dropped, or added based solely on their measured
contribution to net PnL over the benchmark window (Section 3). NHTS may:
* Drop indicators that do not improve performance.
* Add indicators available out-of-the-box in NinjaTrader 8.
* Add custom indicators developed in-house.

Indicator logic is implemented as original hosted calculator classes
(the *Calc classes in NHTS.HostedIndicators.cs) compiled into the single
NHTS.dll. No third-party commercial indicator licenses are required by the end
user. (These calculators replaced the earlier *Equivalent.cs implementations.)

8.2 Current Working Set (baseline, subject to change by benchmark)
  Indicator        Role                     Status
  --------------   ----------------------   -------------------------------------
  AIQ1Calc         Trigger (see 8.3)        Current trigger; mandatory by default
  AAACalc          Confluence voter         Active
  SuperBandsCalc   Confluence voter         Active (no independent validation yet)
  DragonTrendCalc  Confluence voter         Active (direction ~92% vs predecessor)
  EasyTrendCalc    Confluence voter         Active; underperforming — review
  RubyRiverCalc    Confluence voter         Active
  SolarWaveCalc    Confluence voter         Active; SW_Count counter defect (8.4)
  T3ProCalc        Confluence voter         Active (predecessor T3 was unreliable)
  VIDYAProCalc     Confluence voter         DROP CANDIDATE — non-functional (8.4)

8.3 Trigger
* AIQ1Calc is the default / first-choice mandatory trigger, inherited from the
  ninZa.co lineage. Its checkbox is displayed but non-clearable while it remains
  the trigger.
* The trigger is OPEN: AIQ1 may be replaced or removed if the benchmark shows
  this improves performance.
* Dependency note: the current entry mechanism (Yellow/Orange "square" entry
  windows) is built around AIQ1. Replacing the trigger requires reworking that
  entry logic; it is not a drop-in swap.

8.4 Known Functional Defects (independent of any ninZa comparison)
* VIDYAProCalc (VY): IsUptrend is effectively stuck false (the wide filter band,
  FilterMultiplier = 4.0, prevents the up-flip). A frozen input contributes
  nothing to confluence yet still counts toward the total, skewing thresholds.
  Decision pending: fix the calculator to function correctly on its own terms,
  OR drop VY from the roster — whichever yields better benchmark PnL. Given the
  predecessor VIDYAPro was also unreliable, dropping is a leading option.
* SolarWaveCalc (SW_Count): the wave counter runs roughly 5x hot, which can push
  SolarWave to vote (via MinSolarWaveCount) when it should stay silent. Fix the
  counter to behave sensibly; SW direction (SW_IsUp) is functioning (~95%).

8.5 Confluence Threshold
* Default threshold: configurable; default value to be set by the benchmark
  (Section 3), not by matching any predecessor.
* Adjustable by the trader at runtime via the panel.

==============================================================================
9.1 Overview
NHTS displays an on-chart panel (derived from the original ActiveNikiTrader panel

  and inclusion checkbox.

* Confluence count display: e.g. 5/5 indicating current agreeing indicators vs
  threshold.

* Run Analysis button: triggers the analysis pipeline on demand.
* Audio alert toggle.
* Auto-execution toggle.

10. LOGGING ARCHITECTURE
==============================================================================
10.1 Structured Log
NHTS writes a single structured log file in JSON Lines format (.jsonl) — one
JSON object per event — to a configurable location on the client machine. The
log is opened at session start, appended continuously, and closed at session end.

The NHTS .jsonl log is the sole input for the analysis engine. NinjaTrader native
logs are not used by the analysis pipeline. This consolidates data previously
split across the predecessor's .txt log, optional .csv log, and NT8 native logs.

10.2 Log Schema (representative event)
{ "timestamp": "...", "event_type": "signal", "instrument": "NQ",
  "price": 19845.25, "signal_direction": "LONG", "confluence_count": 5,
  "confluence_threshold": 5,
  "indicators": { "AIQ_1": { "direction": "LONG", "included": true,
  "mandatory": true }, ... },
  "order": { "action": "BUY", "auto_executed": true, ... } }

10.3 Secondary Export
CSV export is available as a secondary format generated by the analysis engine at
report time from the .jsonl source, if required. (The current per-bar indicator
CSV used for validation is a development aid and may be retained behind a debug
flag.)

11. ANALYSIS ENGINE
==============================================================================
11.1 Architecture — V1 Hybrid
The analysis engine is packaged as a self-contained Windows executable (built via
pyinstaller from the consolidated Python pipeline). No Python installation is
required on the client machine. The executable is bundled with the NHTS
distribution.

Triggered by:
* One-click via Run Analysis button in the NHTS panel.
* Configurable scheduled task within NHTS settings (e.g. end-of-session, daily).

11.2 Source Scripts
The engine consolidates and streamlines:
* analysis.py    — performance metric computation
* parsers.py     — log ingestion and parsing
* report.py      — report generation (ported to HTML output)
* roundtrips.py  — completed trade reconstruction
* simulation.py  — parameter variation testing
* main.py        — pipeline orchestration
* config.py      — configuration
* Analyze-VPSTrades.ps1 and ActiveNikiNEW_DAY_Analysis.ps1 — retired as
  standalone scripts; logic absorbed into the consolidated pipeline.

11.3 Report Delivery
* Primary: HTML report opened automatically in the default browser. Zero
  configuration required.
* Optional: Email delivery (configurable). Not enabled by default.

11.4 Report Contents
* Trade summary — entries, exits, P&L
* Time slot analysis — per-hour breakdowns with LONG/SHORT splits
* Key insights — profitable windows, underperforming indicators
* Parameter optimization suggestions — trading hours, confluence threshold,
  trailing stop parameters
* Benchmark comparison [NEW] — NHTS vs ActiveNikiTrader net PnL and guardrail
  metrics over the configured window (supports Section 3).

11.5 V2+ — Embedded Analysis
In a future milestone, the analysis logic will be ported to C# and embedded in
the NT8 AddOn UI, eliminating the external executable dependency.
